Images and containers|What is the relationship between an image and a container?|A container is a runtime instance created from an image|Multiple containers can be created from the same image|An image is always a running process|Changing one container automatically changes every image tag|A team edits a running container and expects future instances to include the fix.|Rebuild and version the image with the intended change|Rely on the modified container as the permanent deployment source|Explain images containers and reproducible deployment.
Layering|How are container image changes commonly represented?|As filesystem layers plus image configuration|Later layers can hide earlier files without removing their bytes from older layers|Deleting a file in a later layer always removes it from image history|Every layer is a separate running virtual machine|A secret was copied into an image and deleted in a later step.|Rebuild without the secret and rotate any exposed credential|Assume deleting the visible file erased it from all layers|Explain why image layers matter for secret handling.
Dockerfiles|What does a Dockerfile describe?|Instructions for building an image|Build inputs and base versions affect reproducibility|It is a live process supervisor for every host service|It automatically deploys the image to production|A rebuild unexpectedly uses a changed base image tag.|Review and pin the intended base version or digest|Assume a mutable tag always identifies identical content|Explain how you would make a Docker build reproducible.
Build context|What is the Docker build context?|The set of files made available to the build|A dockerignore file can exclude unnecessary or sensitive inputs|It is only the Dockerfile text|It always excludes credentials automatically|A build sends a large directory containing private files.|Restrict context and add deliberate exclusion rules|Send the whole home directory to simplify COPY commands|Explain how you choose a safe efficient build context.
Container logs|Where should a containerized service commonly send operational logs?|To stdout and stderr for collection by the runtime|Log retention and rotation still need explicit management|Logs sent to stdout can never consume host storage|Docker automatically stores logs forever without capacity cost|Host disk fills because container logs grow without rotation.|Inspect the logging driver and configure bounded retention|Delete arbitrary application data to free space temporarily|Explain container log collection and storage limits.
Port publishing|What does Docker port publishing do?|Map a host endpoint to a container port|Exposing metadata alone does not publish a host port|EXPOSE automatically opens every host firewall|Publishing a port makes application authentication unnecessary|A service listens inside a container but is unreachable on the host port.|Check listener binding and the explicit port mapping|Assume EXPOSE alone created the host mapping|Explain EXPOSE versus publishing a port.
Volumes|Why use a volume for persistent container data?|Its lifecycle can be managed separately from the container writable layer|Volumes still require backup and access controls|Deleting any container always preserves its writable-layer data|Volumes automatically replicate data across all hosts|A database loses data after its container is replaced.|Move persistent data to appropriate managed storage and restore verified backups|Store the only copy in an ephemeral writable layer|Explain storage choices for a containerized database.
Entrypoints|What is a benefit of exec-form ENTRYPOINT for a simple service?|The service can run directly as the container's main process|Signal forwarding differs when an intermediate shell is involved|Exec form starts an interactive shell by default|An intermediate shell always forwards every signal correctly|A service ignores graceful stop because its shell wrapper mishandles signals.|Use exec appropriately and verify stop behavior|Rely on forced termination as the normal lifecycle|Explain entrypoint design and signal handling.
PID one|Why does the container's main process need careful child handling?|It may need to reap children and handle termination signals|A small init can help workloads that spawn child processes|PID one automatically reaps every child in all applications|Container shutdown guarantees every child flushes its data|A worker container accumulates zombie child processes.|Inspect reaping behavior and use suitable process supervision|Restart more frequently without correcting child handling|Explain PID-one responsibilities in a container.
Health checks|What does a Docker health check report?|A health status based on the configured check result|A health status alone does not guarantee automatic container restart|An unhealthy status always restarts the container in standalone Docker|A successful process start proves ongoing application readiness|A container is unhealthy but still running.|Inspect health output and configure the intended supervisory response|Assume the runtime has already restarted it|Explain the difference between running healthy and ready.
User identity|Why run an application as a non-root user when possible?|Reduce the privileges available to compromised application code|Non-root execution complements other isolation controls|A non-root container has no possible security risks|Container root is always equivalent to a fully isolated virtual-machine root|An application needs write access only to one data directory.|Set an appropriate user and narrow directory permissions|Run privileged solely to avoid a file permission error|Explain least privilege in container runtime configuration.
Memory limits|What can a container memory limit cause under excess demand?|The workload can encounter cgroup memory pressure or OOM termination|Host free memory does not negate a container's configured limit|A memory limit only changes monitoring display|A container can always exceed its hard limit if the host is idle|A container dies while the host reports free RAM.|Inspect its limit memory events and working-set demand|Ignore the container limit because host RAM is available|Explain container-specific memory failures.
CPU quotas|What does a CPU quota constrain?|CPU runtime available to the cgroup over scheduling periods|Quota throttling can affect latency|A CPU quota reserves an exclusive physical core automatically|Quota exhaustion always terminates the container|A low-CPU-limit service has high tail latency with throttling.|Compare quota demand and throttling before adjusting limits|Assume low host utilization rules out CPU constraints|Explain CPU quotas versus CPU affinity and shares.
Bind mounts|What distinguishes a bind mount from a named volume?|A bind mount exposes a specified host path|Host path permissions and contents directly affect the container|A bind mount always copies data into the image|Bind mounts are automatically portable across every host|A deployment works on one host but lacks files on another.|Verify the host path and avoid hidden host-specific dependencies|Assume the image contains bind-mounted files|Explain portability risks introduced by bind mounts.
Read-only filesystems|Why use a read-only container root filesystem?|Reduce unintended writes to the image-derived filesystem|Required writable paths must be provisioned separately|Read-only root prevents every network attack|Read-only root makes all mounted volumes read-only automatically|A hardened container fails when writing temporary files.|Provide narrowly scoped writable temporary storage|Make the entire container privileged to allow temporary writes|Explain how you would harden filesystem access without breaking the application.
Multi-stage builds|What is a primary benefit of multi-stage builds?|Separate build tooling from the final runtime image|Only explicitly copied artifacts need enter the final stage|Every intermediate build tool must remain in the runtime image|Multi-stage builds guarantee absence of vulnerabilities|A production image contains compilers and package caches unnecessarily.|Copy required runtime artifacts from a builder into a smaller final stage|Ship the full build environment by default|Explain multi-stage build design and runtime dependency verification.
Build cache|Why order stable dependencies before frequently changing source?|It can preserve useful cached build steps|Cache keys and inputs determine whether a step can be reused|Docker caches every step forever regardless of inputs|A cached build proves dependencies are up to date|A small source edit causes expensive dependency installation every build.|Separate dependency manifests from frequently changing application source|Disable all caching without examining layer order|Explain cache-efficient Dockerfile ordering.
Secrets in builds|How should build-time credentials be supplied where supported?|Use a dedicated build secret mechanism|Secrets should not be baked into layers or ordinary build arguments|Build arguments are always encrypted and excluded from history|Deleting a credential in a later layer guarantees secrecy|A dependency download requires a private registry credential.|Use scoped build secrets and verify the final image contains no credential|COPY a long-lived credential into the image|Explain secure authenticated dependency access during builds.
Image digests|What does an image digest identify?|Specific content-addressed image data|Mutable tags can move to different content|A digest is just a friendly mutable alias|Using latest guarantees reproducible deployments|Two deployments of the same tag run different builds.|Record and deploy the intended immutable digest|Assume the tag name proves identical image contents|Explain tags digests and traceable releases.
Networks|What benefit does a user-defined bridge network provide?|Scoped container connectivity with built-in name resolution|Network attachment and published host ports are distinct choices|Every container name resolves globally across unrelated networks|Joining a bridge publishes every port to the Internet|Two containers expected to communicate are attached to different networks.|Inspect network membership and intended service names|Publish all ports publicly to bypass internal design|Explain container-to-container discovery on a user-defined network.
Compose dependencies|What is a limitation of simple startup ordering?|A started dependency may not yet be ready to serve requests|Readiness checks and application retry behavior remain important|Starting a database process proves schema initialization is complete|Startup ordering eliminates all later dependency failures|An application starts before its database becomes usable.|Use readiness-aware orchestration and bounded connection retries|Add one arbitrary sleep and assume readiness is guaranteed|Explain startup order versus readiness in Compose applications.
Restart policy|What does a restart policy govern?|Runtime behavior when a container exits under specified conditions|Restarting repeatedly does not repair an underlying bad configuration|A restart policy fixes every application bug|Every unhealthy status is equivalent to process exit|A container exits immediately because a required setting is missing.|Inspect exit logs and correct configuration before relying on restarts|Increase restart frequency without reading the error|Explain restart loops and how you would diagnose them.
Registry access|Why separate image pull credentials from application credentials?|They grant different capabilities at different lifecycle stages|Credentials should have the minimum required repository scope|A registry password is always safe to embed in an image|Every application needs permission to push production images|A runtime workload can overwrite the image it was deployed from.|Reduce registry credential scope and separate build from runtime identities|Give every container registry administrator access|Explain least-privilege access to a private image registry.
Resource cleanup|Why inspect Docker objects before pruning?|Unused from the runtime's perspective may still be operationally valuable|Volume deletion can remove persistent data|Every prune operation is harmless to recoverability|All stopped containers and volumes are guaranteed disposable|A host is low on disk and an operator proposes deleting every volume.|Identify consumers and backups before scoped cleanup|Run broad volume deletion without reviewing data ownership|Explain a safe Docker disk-cleanup procedure.
Socket exposure|Why is mounting the Docker daemon socket high risk?|Daemon access can grant extensive control over the host|Treat daemon API access as a privileged trust boundary|The socket grants only read-only log access by default|A non-root process cannot misuse a mounted daemon socket|A web application mounts the daemon socket for convenience.|Remove unnecessary daemon access or isolate a narrowly controlled service|Assume container isolation neutralizes daemon API privileges|Explain the risks of Docker socket access inside a container.
Rootless mode|What does rootless Docker aim to reduce?|The need for a root-privileged daemon and containers|Rootless operation has compatibility and resource-control considerations|Rootless mode removes all kernel attack surface|Rootless mode guarantees every privileged workload works unchanged|A team wants to reduce daemon privilege on developer hosts.|Evaluate rootless support against networking storage and workload requirements|Assume rootless operation has no behavioral constraints|Explain rootless Docker benefits and limitations.
Image scanning|What does a vulnerability scan provide?|Evidence about known issues in the inspected image and metadata|A clean scan is not proof of absence of all vulnerabilities|Scanning guarantees application logic is secure|A scan replaces dependency updates and runtime controls|A scan finds a critical library issue in a deployed image.|Assess reachability and impact then rebuild and redeploy a verified fix|Edit the running container and leave the vulnerable image unchanged|Explain how scanning fits into image maintenance.
Supply chain|Why verify image provenance or signatures?|Establish evidence about artifact origin and integrity|Verification policy must define trusted identities and sources|Any signed image is automatically safe regardless of signer|A signature proves the application has no bugs|A registry contains an unexpected image under a trusted-looking tag.|Verify digest provenance and the authorized publishing identity|Trust the artifact solely because its tag resembles a release|Explain a trustworthy container artifact promotion process.
Shared kernel|What security implication follows from containers sharing a host kernel?|Kernel vulnerabilities can cross container isolation boundaries|Host patching remains important even with minimal images|Each container always has an independent kernel|Updating only application packages patches the host kernel|A host kernel vulnerability affects container isolation.|Assess host exposure and roll out host remediation safely|Assume rebuilding application images alone fixes the kernel|Compare container and virtual-machine isolation boundaries.
