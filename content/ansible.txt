Inventory|What does an Ansible inventory describe?|Managed hosts and their grouping or connection data|Inventory selection determines the potential execution scope|It is a list of Docker image layers|It automatically grants access to every listed host|A production play unexpectedly targets a staging group too.|Inspect inventory groups and the resolved host pattern before execution|Assume the playbook filename limits the hosts|Explain how you verify Ansible target scope.
Playbooks|What does a playbook organize?|Plays mapping tasks and roles to target hosts|Task order and conditions affect execution behavior|It is only a database of passwords|It always runs every task on every inventory host|A task intended for web servers runs on database hosts.|Correct the play's host selection and verify the resolved list|Rename the playbook without changing target selection|Explain play structure and host targeting.
Modules|Why prefer purpose-built modules over shell commands?|Modules often model desired state and support idempotent behavior|Module documentation defines supported parameters and return values|Every shell command is automatically idempotent|Modules never require privileges or remote dependencies|A shell task appends the same configuration line on every run.|Use an appropriate declarative file or configuration module|Suppress the repeated output while continuing duplicate writes|Explain module selection for repeatable configuration.
Idempotence|What does idempotence mean for a configuration task?|Repeated execution can preserve the already-correct desired state|A no-change run is useful evidence but not a complete correctness proof|An idempotent task must execute exactly once forever|Idempotence means every task reports changed|A second identical run still recreates an unchanged configuration file.|Inspect task behavior and use state-aware operations|Ignore change reporting because repeated restarts are harmless|Explain how you test idempotence in automation.
Become|What does become enable?|Privilege escalation for selected operations|Escalation should be scoped to tasks that need it|It automatically encrypts all variables|It makes every remote command safe|A task needs root only to install one package.|Scope privilege escalation and use the package module|Run every unrelated task with unrestricted root privileges|Explain least privilege in an Ansible playbook.
Variables|What is an important property of Ansible variables?|Values can come from multiple sources with precedence rules|Unexpected values should be traced to their actual source|The last alphabetic variable name always wins|All variable sources have identical precedence|A host uses a different port than its role default.|Inspect higher-precedence inventory and runtime overrides|Edit defaults repeatedly without checking overrides|Explain how you troubleshoot an unexpected variable value.
Facts|What are gathered facts typically used for?|Discover host characteristics for conditional automation|Facts can become stale if cached beyond relevant changes|Facts are always a live view of every host property|Facts automatically fix an unhealthy host|A cached operating-system fact no longer matches a rebuilt host.|Refresh relevant facts and inspect cache policy|Assume cached facts are permanently authoritative|Explain useful and risky uses of fact caching.
Handlers|When are notified handlers normally run?|At defined handler execution points after notifying changes|Multiple notifications can coalesce into one handler execution|Every handler runs after every task unconditionally|A handler name is just a task comment|Three configuration tasks require one service restart.|Notify a shared handler and verify the restart timing|Restart the service unconditionally after every task|Explain handlers and how they reduce unnecessary restarts.
Check mode|What is a limitation of Ansible check mode?|Support and predictive accuracy depend on the module and task|A dry run does not prove every runtime side effect is safe|Check mode guarantees an exact simulation of every shell command|A passing check run replaces all execution testing|A task depends on output from a command skipped in check mode.|Review check-mode support and test safely in a representative environment|Treat the incomplete dry run as proof of production success|Explain how you use check mode without overtrusting it.

Vault|What does Ansible Vault protect?|Encrypted content at rest when properly managed|Decrypted values can still leak through task output or external systems|Vault prevents every runtime secret exposure|Vault removes the need to protect decryption credentials|An encrypted secret is printed by a debug task.|Remove the disclosure and protect runtime logging|Assume the value remains encrypted after decryption for use|Explain Vault's protection boundary.
Templates|What does a Jinja template allow?|Render configuration from variables and expressions|Rendered configuration should be validated before service activation|Templates guarantee valid syntax for every target service|Every template render must restart the service|A rendered web-server configuration has invalid syntax.|Validate the candidate configuration before replacing or reloading it|Restart the service first and inspect syntax afterward|Explain safe template deployment with validation.
Roles|What does an Ansible role package?|Related tasks defaults handlers and supporting files|Roles benefit from explicit interfaces and limited assumptions|A role is necessarily a separate remote user account|Roles automatically isolate all variables from every other role|A shared role requires undocumented variables and breaks callers.|Document defaults and required inputs and test representative callers|Add more hidden inventory assumptions|Explain a maintainable reusable role interface.
Collections|What is an Ansible collection used for?|Distribute related modules plugins and roles|Pinning tested collection versions helps reproducibility|Collections are always included in every ansible-core installation|Collection upgrades can never change behavior|CI fails because a module collection is absent on a clean runner.|Declare and install versioned collection requirements|Rely on packages installed manually on one developer machine|Explain dependency management for Ansible projects.
FQCNs|Why use fully qualified collection names for modules?|Make the intended module namespace explicit|Explicit names reduce ambiguity when collections overlap|A fully qualified name automatically grants more privileges|Short names are always globally unique across all collections|Two collections provide similarly named modules.|Use the intended collection namespace and verify its documentation|Assume the first short-name match is always correct|Explain module naming and collection resolution.
Conditionals|What does a when expression control?|Whether a task executes for a host based on a condition|Conditions should use correctly typed and available values|It changes inventory membership permanently|It forces every task to execute at least once|A task unexpectedly runs because a string value was treated as truthy.|Normalize input types and inspect the condition|Assume the text false is always a boolean in every context|Explain robust conditional logic in playbooks.
Registered results|What does register capture?|A task result for later use in the play|Result fields depend on the module and execution outcome|Register stores a permanent system environment variable|Every result has identical fields even when skipped|A later task accesses stdout on a skipped result.|Guard for skipped or missing result fields|Assume every prior task produced stdout|Explain defensive handling of task results.
Loops|Why choose loop variable names deliberately?|Avoid variable collisions in nested or included tasks|Loop results often require handling a collection of per-item results|A loop always executes on all hosts serially|Every loop result is a single scalar stdout value|An included task overwrites the outer item variable.|Use loop_control with distinct variable names|Reuse item at every nesting level without checking|Explain nested loops and registered loop results.
Failure conditions|What does failed_when customize?|The condition under which a task is considered failed|Exit status and output semantics should guide failure criteria|It suppresses all future errors automatically|It changes the remote command's actual side effects|A command returns a documented nonzero code for a harmless state.|Define an explicit failure condition matching the command contract|Ignore all nonzero returns without distinguishing real failures|Explain custom failure handling without hiding errors.

Blocks and rescue|What is a rescue block useful for?|Handle qualifying task failures with recovery steps|Recovery logic must still account for partial side effects|Rescue automatically rolls back every previous change|Every unreachable-host condition is handled exactly like an ordinary task failure|A deployment task fails after writing part of its configuration.|Use explicit recovery and verify the resulting host state|Assume block syntax provides automatic transaction rollback|Explain structured error handling and its limits.
