Service managers|What is a service manager responsible for?|Managing configured service lifecycle and supervision|A running process and a healthy service are different observations|Starting a service proves all business operations succeed|A service manager replaces every application health check|A service is active but its endpoint returns errors.|Inspect application health and logs alongside unit status|Declare success solely from an active status|Explain service lifecycle versus application readiness.
Enable versus start|What does enabling a systemd service generally configure?|Activation through configured unit installation relationships such as boot targets|Enabling and starting are separate operations unless explicitly combined|Enable always starts the process immediately|Start always enables the service on future boots|A service works now but does not return after reboot.|Inspect enablement and the intended boot activation path|Assume a successful manual start persists boot configuration|Explain systemd enable start and their operational differences.
Unit overrides|Why use a systemd drop-in override?|Customize a unit without directly editing a vendor-supplied unit file|Configuration changes may require daemon reload and service action|Drop-ins are ignored whenever packages update|Editing a vendor file is the only supported customization method|A package upgrade replaces local service tuning.|Use a managed drop-in and verify the effective unit configuration|Keep re-editing package-owned files after each upgrade|Explain maintainable service configuration overrides.
Journals|What is journalctl useful for?|Querying journal records with filters such as unit and time|Retention and persistence settings determine available history|The journal always retains all logs forever|Journal entries automatically contain every application event|A restart failure needs investigation around a known time.|Query the relevant unit and time window|Search every unrelated log without narrowing the incident window|Explain focused journal-based service troubleshooting.
Accounts|Why use separate service accounts?|Limit access and attribute activity to distinct workloads|Account separation must be paired with appropriate permissions|Separate usernames automatically isolate all files and networks|Every service should share one administrator account|One service account can read unrelated applications' secrets.|Separate identities and narrow file and service access|Rely on naming conventions without changing permissions|Explain service identity isolation on a shared host.
SSH keys|Why protect private SSH keys?|Possession can enable authentication wherever the key is trusted|Key removal and rotation require reviewing authorized locations|A private key is safe to publish if the username is hidden|A public key must remain secret like a password|A private deployment key appears in a shared log.|Revoke or rotate the key and review affected access|Delete only the visible log line and keep using the key|Explain response to an exposed SSH private key.
Package management|Why prefer the distribution package manager for system packages?|It tracks package ownership dependencies and updates|Third-party sources still require trust and version review|A package manager proves every package is vulnerability-free|Copying random binaries always improves reproducibility|A critical library was installed manually outside package tracking.|Inventory the installation and establish a supported update path|Assume untracked software receives normal package security updates|Explain maintaining an auditable system software inventory.
Scheduled jobs|Why define explicit environments for scheduled jobs?|They may run with different PATH working directory and credentials|Use explicit paths and controlled output handling|Cron always inherits an interactive shell's full environment|Scheduled jobs always run as the currently logged-in user|A script works interactively but fails under the scheduler.|Compare identity environment paths and working directory|Add arbitrary delays without inspecting the execution context|Explain reliable scheduled-job design.
Time synchronization|Why does consistent system time matter operationally?|Authentication log correlation and distributed behavior can depend on it|Elapsed-time measurement may need monotonic clocks separately|Clock synchronization makes all machines perfectly simultaneous forever|Wall-clock timestamps alone establish exact distributed event order|Authentication failures coincide with clock drift.|Inspect synchronization state and correct the time source safely|Disable time synchronization permanently|Explain clock drift detection and its operational impact.
Disk layout|Why separate growth-prone data from critical system paths?|Reduce the chance one workload exhausts space needed for core operation|Capacity limits and monitoring still matter after separation|Separate directories alone always mean separate capacity|A separate partition can never fill up|Application logs fill the root filesystem and disrupt system services.|Bound log growth and evaluate storage isolation|Keep increasing log verbosity on the full filesystem|Explain disk layout and capacity protection for production hosts.
Log rotation|What should log rotation include beyond renaming files?|A retention policy and appropriate application file-handle behavior|A process may keep writing to a renamed or deleted open file|Renaming a log guarantees the process reopens a new file|Rotation automatically archives logs to independent backup storage|Disk usage remains high after a log file was deleted.|Inspect open handles and use the application's supported reopen mechanism|Delete more active files without checking their owners|Explain safe log rotation and open-file behavior.
Backups|What distinguishes a backup from a second live copy?|Recoverable retained data protected from relevant failure modes|Replication can propagate accidental deletion or corruption|Replication always replaces historical backups|A backup is useful even if it cannot be restored|An operator deletes data and replication mirrors the deletion.|Restore from a verified retained recovery point|Assume the live replica necessarily contains the pre-deletion state|Explain backups versus replication.
Restore verification|What should a restore test verify?|Data integrity and usable application behavior after recovery|Recovery time and required credentials belong in the test|A completed file copy proves the application can recover|A restore test never needs application-level checks|A restored database starts but required records are missing.|Validate business-relevant data and recovery-point expectations|Declare success solely because the database process runs|Explain acceptance criteria for a restore exercise.
RAID|What is a limitation of RAID?|It does not protect against every logical deletion or corruption event|Redundancy and independent backups solve different problems|RAID makes backups unnecessary|Any RAID level survives any number of disk failures|An administrator deletes a directory on a redundant array.|Recover from appropriate backups rather than expecting redundancy to undo deletion|Wait for RAID to reconstruct intentionally deleted files|Explain redundancy versus recoverability.
LVM|What does logical volume management provide?|An abstraction for allocating logical storage from physical capacity|Filesystem resizing requirements are separate from volume resizing|Growing a logical volume always grows every filesystem automatically|Shrinking any filesystem online is always supported|A logical volume was extended but df shows unchanged capacity.|Check and perform the filesystem-specific growth step safely|Assume the extra blocks are immediately usable by every filesystem|Explain layered storage resizing and verification.
Filesystem mounts|Why use stable device identifiers in mount configuration?|Device enumeration names can change across boots|Mount configuration should be tested before a critical reboot|A disk always keeps the same enumeration name forever|A mount entry guarantees the underlying disk is healthy|A host mounts the wrong volume after device ordering changes.|Use stable identifiers and verify mount dependencies|Hard-code whichever device name appeared during one boot|Explain reliable persistent mount configuration.
Boot recovery|What is a safe first step when a host fails after a boot configuration change?|Use an authorized recovery path and inspect the specific boot failure|Keep a known recovery route before making risky boot changes|Repeated blind rebooting repairs every configuration error|Boot failures always prove the physical disk is dead|A modified mount entry prevents normal boot.|Use recovery access to inspect and correct the faulty entry|Reinstall the entire system before checking the recent change|Explain a controlled response to a boot-time configuration failure.
Patching|What should a patch rollout include?|Representative validation staged deployment and recovery planning|Some updates require service restart or reboot to take effect|Installing a package proves all running processes use the new code|Every patch should be deployed fleet-wide without observation|A kernel update is installed but the old kernel remains running.|Plan and verify the required reboot within availability constraints|Assume the package version proves the active kernel changed|Explain patch verification for running systems.
Configuration drift|Why monitor configuration drift?|Untracked changes can undermine reproducibility and policy|Intentional emergency changes need reconciliation into the managed baseline|Every manual change is malicious|Configuration management guarantees drift can never occur|A host differs from its declared baseline after incident mitigation.|Review the change and adopt or revert it deliberately|Overwrite the mitigation blindly during the active incident|Explain closing the loop after emergency configuration changes.
Access reviews|Why periodically review privileged access?|Roles and operational needs change over time|Removal should account for service dependencies and emergency access|Once granted privileged access should never expire|A username alone proves current authorization need|A departed team member retains production administrative access.|Revoke access through the managed identity path and audit related credentials|Leave access active indefinitely in case it becomes convenient|Explain a practical privileged-access review.
Sudo policy|Why scope sudo permissions carefully?|Privileged commands can expose more capability than their names suggest|Editors shells and writable command paths can enable escalation|Allowing any editor as root is always harmless|A command allowlist makes argument handling irrelevant|A restricted sudo rule permits a tool that can launch arbitrary shells.|Review effective capabilities and narrow the allowed operation|Assume the command's friendly name guarantees limited privilege|Explain pitfalls in designing restricted sudo rules.
Resource limits|Why set service-specific resource limits?|Contain resource consumption and protect shared capacity|Limits must be tested against legitimate workload needs|Any low limit improves reliability without trade-offs|One host-wide limit is optimal for every service|A service fails under load after an aggressive descriptor limit.|Compare legitimate demand with observed usage and tune deliberately|Raise every limit without investigating possible leaks|Explain balancing containment with service capacity.
System monitoring|Why monitor both resource and service indicators?|Resource pressure and user-visible behavior provide complementary evidence|A healthy host metric alone does not prove application success|Low CPU guarantees healthy service behavior|Application failures always appear as high memory use|Users see errors while host resources look normal.|Inspect application and dependency indicators alongside host health|Dismiss the incident because system graphs are green|Explain a useful monitoring model for a production host.
Immutable hosts|What is an advantage of replacing hosts from a known image?|Reduce divergence caused by accumulated manual changes|Persistent data and identity must survive through explicit design|Replacing a host automatically preserves all local mutable data|An image removes the need to patch dependencies|A manually repaired host cannot be reproduced elsewhere.|Capture the intended configuration and rebuild a tested image|Keep the unique host forever as the only source of truth|Explain immutable infrastructure and its state-management requirements.
Capacity forecasts|Why consider growth and failure scenarios in capacity forecasts?|Normal averages can underestimate future or degraded-mode demand|Forecasts should be checked against observed trends and load tests|Current free space guarantees next month's capacity|Capacity planning is unnecessary when monitoring exists|Storage growth will exhaust capacity before the procurement lead time.|Project the trend and act before the required lead time is consumed|Wait for a full-disk alert before arranging capacity|Explain proactive capacity management.
Remote administration|Why preserve an independent recovery path during network changes?|A faulty change can cut off the primary management connection|Test and stage changes with a rollback path|An SSH session guarantees permanent recovery access|Remote firewall edits cannot affect the current operator|A firewall change risks removing management access.|Use staged rules and verified console or rollback access|Apply an untested deny-all rule over the only SSH session|Explain safe remote network maintenance.
Data sanitization|Why distinguish file deletion from secure media disposal?|Deleted data may remain recoverable depending on storage and controls|Disposal procedures must match media technology and sensitivity|Deleting a filename always overwrites every physical copy|One universal overwrite command is correct for all storage media|A retired disk contains sensitive production data.|Follow an approved media-specific sanitization or destruction process|Assume emptying a directory securely erased the disk|Explain the operational difference between deletion and sanitization.
Fleet changes|Why use staged rollouts for system configuration?|Limit impact and observe behavior before wider deployment|Canaries should represent important workload variations|A successful change on one idle host proves fleet-wide safety|The fastest rollout always minimizes risk|A kernel setting works on one host but harms busy database hosts.|Test representative groups and expand with monitored stop criteria|Apply globally based only on the idle-host result|Explain representative canaries for heterogeneous fleets.
Disaster documentation|What must recovery documentation include to be usable?|Dependencies access requirements verification and responsible owners|Recovery instructions should be accessible during the failure they address|Documentation stored only on the failed system is sufficient|A list of server names is a complete recovery plan|A recovery team cannot access the instructions because identity services are down.|Provide an authorized resilient documentation and access path|Store the only recovery guide behind the same unavailable dependency|Explain avoiding circular dependencies in recovery plans.
Change verification|What should follow a successful administration command?|Verify the intended system outcome and relevant side effects|Exit status is evidence about the command rather than complete service health|Exit code zero proves every user workflow is healthy|Verification is unnecessary after an automated command|A reload command succeeds but requests still fail.|Check service behavior logs and the actual loaded configuration|Close the incident solely because the command returned zero|Explain outcome-based verification after operational changes.
